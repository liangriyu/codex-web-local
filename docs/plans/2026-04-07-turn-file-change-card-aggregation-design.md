# Turn 级文件变更聚合卡片与历史单文件 Diff 设计

## 背景

当前仓库已经支持：

- 按 `turnId` 维护文件变更时间线
- 在消息流中展示历史文件变更卡片
- 对当前线程最新一组可逆变更执行撤销 / 重新应用

但在实际使用中仍有三个明显问题：

1. 同一个 `turn` 内如果有多条 assistant 消息，文件变更卡片会重复挂在每条消息后面，导致同一组会话改动被拆散。
2. 同一个文件如果在两次不同 `turn` 中都被修改，用户需要看到两份不同的历史 diff，但当前 UI 没有把“这是该次会话的单文件 diff”表达清楚。
3. 卡片内虽然已有文件行，但缺少明确的“查看 Diff”按钮，用户很难感知这是可单独打开查看的历史单文件 diff。

## 目标

- 同一 `turn` 的文件变更只展示一张聚合卡片
- 聚合卡片挂在该 `turn` 最后一条 assistant 消息后面
- 卡片内每个文件都提供明确的 `查看 Diff` 按钮
- 同一路径在不同 `turn` 中保留各自独立的历史 diff
- 最新一组可逆变更继续支持 `撤销本次变更` / `重新应用本次变更`
- 历史 diff 继续复用右侧预览面板，但明确区分它不是当前 workspace diff

## 非目标

- 不把多次 `turn` 的文件变更再聚合成线程级大卡片
- 不支持任意历史 `turn` 的撤销 / 重新应用
- 不在本轮重做 `CodePreviewPanel` 的整体布局
- 不调整服务端 patch ledger 的核心结构

## 问题分析

### 1. 当前重复挂卡的根因

现在卡片命中逻辑是：

- 根据 `message.turnId` 查找 `UiThreadTurnFileChangeRecord`
- 只要命中就直接在该消息后渲染卡片

这意味着同一个 `turn` 内若有多条 assistant 消息，所有共享同一 `turnId` 的消息都会命中同一条记录，于是出现重复卡片。

### 2. 单文件历史 diff 的正确语义

同一个文件在两个不同 `turn` 中被修改时，展示的应该是两份不同的 diff，因为主键是：

- `threadId + turnId + file.path`

而不是单纯的 `file.path`。

换句话说，卡片表达的是“这一次会话改了什么”，不是“这个文件当前变成了什么”。因此：

- `turn A` 中的 `src/a.ts` diff
- `turn B` 中的 `src/a.ts` diff

必须作为两份独立历史记录存在并可分别查看。

### 3. 当前 UI 主要是表达不清，而不完全是能力缺失

卡片中的文件行理论上已经带有该次历史 diff 数据，但交互问题在于：

- 文件行像摘要，不像显式动作
- 用户不容易理解点击后看到的是“这次会话的单文件 diff”
- 历史 diff 与 workspace diff 共享同一右侧预览入口，语义容易混淆

## 方案对比

### 方案 A：保留当前按消息命中，只优化文案

做法：

- 保持现有每条命中消息都渲染卡片
- 只给文件行增加 `查看 Diff` 文案

优点：

- 改动最小

缺点：

- 同一 `turn` 仍然被拆散
- 无法形成“这是一组会话变更”的稳定心智

### 方案 B：同 turn 聚合，挂在最后一条 assistant 消息后

做法：

- 一个 `turn` 只渲染一张卡片
- 仅在该 `turn` 最后一条 assistant 消息后渲染
- 每个文件行右侧增加显式 `查看 Diff` 按钮
- 最新可逆 `turn` 继续显示撤销 / 重放按钮

优点：

- 会话边界清晰
- 阅读顺序自然，先看本轮回复，再看本轮改动
- 不需要推翻已有 turn 级时间线数据结构

缺点：

- 需要额外计算“该 turn 最后一条 assistant 消息”

### 方案 C：把卡片从消息流抽出来，做成 turn 分组尾块

做法：

- 消息列表按 `turnId` 分组
- 卡片挂在 turn 分组末尾，而不是某条消息后面

优点：

- 语义最严格

缺点：

- UI 改动更大
- 需要明显重构消息流渲染结构

结论：采用方案 B。

## 推荐设计

### 1. 挂载规则

文件变更卡片只在以下条件同时成立时渲染：

- 当前消息属于 assistant
- 当前消息存在 `turnId`
- 该 `turnId` 存在文件变更记录
- 当前消息是该 `turnId` 下最后一条 assistant 消息

效果：

- 同一 `turn` 内只展示一张卡片
- 卡片稳定挂在本轮最后一条 assistant 消息后面

### 2. 单文件查看 Diff 规则

卡片内每个文件行调整为两段式：

- 左侧：文件路径、行数统计
- 右侧：显式按钮 `查看 Diff`

点击按钮后：

- 打开右侧代码预览面板
- 展示该 `turn`、该文件的历史 diff
- 标题或上下文文案明确这是“本次会话变更”，不是当前 workspace diff

### 3. 同文件多次修改的显示规则

如果 `src/a.ts` 在两个不同 `turn` 中都出现：

- `turn A` 的聚合卡片内展示 `src/a.ts` 的 diff A
- `turn B` 的聚合卡片内展示 `src/a.ts` 的 diff B

二者互不覆盖，也不按路径合并。

### 4. 最新一组可逆变更的操作规则

只有满足 `record.canUndo` 或 `record.canReapply` 的卡片才展示操作区：

- `撤销本次变更`
- `重新应用本次变更`

历史其他卡片只读，不显示写操作按钮。

### 5. 预览语义

右侧预览面板保持复用，但内部语义区分为两类：

- `workspace diff`
- `history turn file diff`

这样用户在点击 `查看 Diff` 时，看到的是该次会话的单文件历史 diff，而不是当前工作区状态。

## 验收标准

- 同一 `turn` 内有多条 assistant 消息时，文件变更卡片只渲染一次
- 卡片挂在该 `turn` 最后一条 assistant 消息后面
- 卡片内每个文件都有明确 `查看 Diff` 按钮
- 点击后打开该 `turn`、该文件的历史 diff 预览
- 同一路径在不同 `turn` 中可以分别打开各自不同的 diff
- 最新一组可逆变更卡片继续支持撤销 / 重新应用
- `npm run build` 通过

## 风险与取舍

- 如果未来消息流需要按 `turn` 分组，当前“最后一条 assistant 消息后挂卡”的实现需要再调整一次，但这比现在直接重构 turn 分组风险更低。
- 右侧预览面板仍被复用，因此必须在文案和面板上下文上明确“历史 diff”与“workspace diff”的差异，否则会继续造成误解。
- 该方案不需要新增服务端协议，主要是前端挂载条件与交互语义修正，属于低风险收敛。
