# 共享 `codex app` 会话强共享设计

## 背景

- 当前 `codex-web-local` 的账号体系处于混合态：
  - 默认 profile 直接绑定基础 `CODEX_HOME`，通常等于 `codex app` 默认账号目录。
  - 额外 profile 使用 `~/.codex/codex-web-local/profiles/<id>` 独立目录。
  - 切换 profile 时会复制部分会话与日志物料，试图延续上下文。
- 这套设计能提供“多账号可切换”的表面能力，但不能提供真正的账号强共享或会话强共享。
- 目标是反过来收敛：优先共享 `codex app`，并尽量做到会话强共享。

## 问题定义

本次讨论的目标不是“让 Web 也能切账号”，而是：

1. `web-local` 与桌面 `codex app` 尽量共享同一个活跃账号。
2. 手机端和桌面端尽量像在操作同一个实时会话。
3. 明确哪些能力能做到强共享，哪些只能做到弱一致。

## 现状批判

### 1. 运行时不是单一事实源

- `web-local` 当前自己拉起并控制 `codex app-server` 进程。
- 这意味着即使共享了同一个 `CODEX_HOME`，Web 端和桌面端也不一定连接同一个活体运行时。
- 结果是：
  - 正在执行的 turn 不保证一致。
  - pending approvals、实时通知流、UI 内存态不保证一致。
  - “看到同一份历史文件”不等于“连接同一个实时会话”。

### 2. 账号模型混合了共享与隔离

- 默认 profile 共享 `codex app` 默认目录。
- 其他 profile 独立隔离。
- 用户无法稳定理解：
  - 哪次切换会影响桌面端默认账号。
  - 哪次切换只影响 Web 自己。

### 3. profile 切换混入了会话迁移语义

- 当前 profile 切换会复制 `state_5.sqlite`、`logs_*.sqlite`、`session_index.jsonl`、`sessions/` 等物料。
- 这说明系统并没有单一会话事实源，而是在做近似复制。
- 这会引入两个长期问题：
  - 隔离不干净：切账号可能带走不该带走的历史与共享会话。
  - 一致性不成立：复制不是实时同步，更不是并发控制。

### 4. “账号共享”被误当成“会话共享”

- 即使所有 profile 都最终指向同一套默认账号，也只能保证身份接近统一。
- 无法保证：
  - 实时 turn 状态一致
  - 并发发送一致
  - 审批归属一致
  - 会话恢复点一致

## 目标约束

### 必须满足

- 共享模式下只有一个活跃账号事实源。
- 共享模式下不能依赖 profile 文件复制维持会话连续性。
- 共享模式下要有明确的并发控制模型。
- 对用户清楚区分：
  - 共享模式：面向 `codex app`
  - 独立模式：面向 `web-local` 自己

### 明确不追求

- 不在第一版实现多账号同时在线。
- 不在第一版实现多端同时可写且自动合并。
- 不在第一版解决断线重连后的复杂冲突合并。

## 可选方案

### 方案 A：继续增强当前混合态

做法：
- 保留默认 profile 绑定 `~/.codex`。
- 保留额外 profile 独立目录。
- 切换时继续复制会话物料。
- 增加“设为默认账号”动作。

优点：
- 改动最小。
- 基本复用当前 profile UI 和服务端存储。

缺点：
- 架构语义继续混乱。
- 仍然没有单一运行时。
- 仍然做不到会话强共享。
- 用户仍然无法判断当前切换是否会影响桌面端。

结论：
- 不推荐。
- 它只会把当前混合态包装得更复杂，不会真正逼近强共享目标。

### 方案 B：强共享模式与独立模式并存

做法：
- 新增“共享模式”：
  - `web-local` 连接已有 `codex app-server`。
  - 当前账号就是共享 `app-server` 的当前账号。
  - 不使用 profile 作为运行态身份源。
- 保留“独立模式”：
  - `web-local` 自己启动 `app-server`。
  - 可继续保留 profile 能力。

优点：
- 架构语义清晰。
- 共享模式下有机会实现账号强共享和会话近强共享。
- 独立模式作为兼容与回退路径。

缺点：
- 需要引入 attach 能力、运行模式检测和更多状态分支。
- 共享模式与独立模式的 UI 提示必须非常明确。

结论：
- 推荐。
- 这是最小可行且可维护的演进路径。

### 方案 C：完全放弃 profile，只做纯共享

做法：
- `web-local` 完全不保留自己的 profile。
- 所有账号操作都直接作用于 `codex app` 默认账号。
- 只支持附着共享运行时。

优点：
- 最纯粹。
- 用户心智最简单。

缺点：
- 回退能力差。
- 失去独立模式和实验空间。
- 上游 attach 能力或运行方式一旦受限，整个产品可用性明显下降。

结论：
- 可作为长期方向，但不适合作为当前仓库的最小可行改造路线。

## 推荐方案

推荐采用 **方案 B：强共享模式与独立模式并存**。

核心原因：

- 它把“共享 `codex app`”和“Web 自主管理 profile”明确分成两种模式，而不是继续混在同一模式里。
- 它允许先在共享模式下实现单账号、单运行时、单 owner 的强共享 MVP。
- 它保留独立模式，降低改造风险，也方便在 attach 不可用时降级。

## 推荐架构

### 1. 运行模式

新增两种显式运行模式：

- `shared`
  - `web-local` 作为客户端连接现有 `codex app-server`
  - 目标是账号强共享与会话近强共享
- `isolated`
  - `web-local` 继续自己启动 `codex app-server`
  - 支持 profile、多账号切换
  - 明确不承诺会话强共享

共享模式应成为推荐模式。

### 2. 单一运行时

共享模式下的关键要求：

- `web-local` 不能再以“切 `CODEX_HOME` 并重启自己管理的 app-server”作为共享手段。
- Web 和桌面端必须连接到同一个 `app-server` 运行时实例。
- 所有线程、审批、通知、账号状态从同一进程读取。

这一步是会话强共享的必要条件。

### 3. 账号模型

共享模式下：

- 当前账号 = 共享 `app-server` 当前账号
- 不再使用 profile 作为活跃账号来源
- profile 若继续保留，只能退化为：
  - 候选账号缓存
  - 登录快捷入口
  - 桌面端辅助切换名册

也就是说，profile 不能再决定共享模式中的真实运行态账号。

### 4. 会话控制权

共享模式下引入最小 owner 机制：

- 每个共享会话只有一个当前操作者：
  - `web`
  - `desktop`
  - `none`
- 空闲时谁先发起 turn，谁获得 owner。
- 运行中另一端默认只读，不允许直接并发发起新 turn。
- 可提供“接管控制权”动作，但必须显式确认。

这是最小并发控制，不做这层就不可能避免双端写冲突。

### 5. 事件流优先

共享模式下：

- 实时通知流是主通道。
- `thread/read`、`thread/list`、`account/read` 只用于冷启动恢复和断线补偿。
- 不再以 profile 切换后的全量 refresh 作为主要同步方式。

### 6. 禁止会话复制

共享模式下必须停掉以下思路：

- 切账号复制 sqlite bundle
- 切 profile 复制 `sessions/`
- 用文件同步模拟实时共享

共享模式只允许：

- 单一运行时
- 单一事实源
- 单一 owner 控制

## 最小数据模型

共享模式新增的重点状态不是 profile，而是共享控制态：

- `serverConnectionMode`: `shared | isolated`
- `sharedSessionOwner`: `web | desktop | none`
- `sharedSessionState`: `idle | running | needs_attention | failed | interrupted`
- `ownerLastSeenAt`
- `pendingApprovalsCount`
- `takeoverRequestedBy`

独立模式下才继续保留：

- `activeProfileId`
- `profiles`

## 最小交互流程

### 启动

1. `web-local` 尝试连接现有 `codex app-server`
2. 成功则进入共享模式
3. 失败则提示：
   - 切到独立模式
   - 或提示先启动/开放桌面端 `app-server`

### 发起会话操作

1. 打开线程时先读取 owner
2. 若 owner 为 `none`，当前端可取得 owner
3. 若 owner 为另一端且线程正在运行，当前端只读
4. 若用户选择接管，则发送显式接管动作并刷新 owner

### 切换账号

共享模式下：

- 切换账号是全局动作，不是局部 Web 动作
- 若存在运行中 turn，则禁止切换
- 切换后桌面和 Web 都需要同步刷新账号状态

独立模式下：

- 继续允许 profile 切换
- 但文案明确：这不会保证与桌面 `codex app` 强共享

## 迁移策略

### Phase 1：模式拆分

- 新增 `shared` / `isolated` 模式概念
- 先不删除现有 profile 存储
- 共享模式下隐藏 profile 切换入口

### Phase 2：共享模式 MVP

- 接入 attach 到现有 `app-server`
- 引入 owner 只读/接管机制
- 共享模式下禁用文件复制逻辑

### Phase 3：收敛默认心智

- README、运行文档、账号中心文案全部改成模式化表述
- 将“会话强共享仅在共享模式下尝试保证”写清楚

### Phase 4：清理历史包袱

- 评估是否移除默认 profile 直连 `~/.codex`
- 评估是否将 profile 完全限制在独立模式

## 主要风险

### 1. 上游 attach 能力不足

- 若 `codex app` 无法稳定暴露可连接的 `app-server`，共享模式会被卡住。
- 这是当前方案的最大外部依赖。

### 2. owner 机制带来交互摩擦

- 用户会感觉“为什么另一端不能直接继续输入”。
- 但不引入 owner，强共享会立刻退化成并发冲突。

### 3. 共享模式下账号切换是高破坏动作

- 必须明确提示“这将影响桌面端当前默认账号”。
- 必须禁止在运行中切换。

### 4. 现有 profile 心智需要迁移

- 用户会从“Web 能自己多账号切换”迁移到“共享模式下只有一个活跃账号”。
- 文档和 UI 提示必须提前到位。

## 验收口径

共享模式的最小成功标准：

- Web 与桌面端连接同一个 `app-server` 实例。
- Web 发起的账号切换能同步反映到桌面端。
- 同一个线程运行时，另一端不会无保护地并发写入。
- 不再依赖 profile 文件复制来延续共享会话。

独立模式的最小成功标准：

- 继续支持当前 profile 方案。
- 文档明确说明独立模式不保证与桌面端会话强共享。

## 结论

- 想做到会话强共享，不能继续围绕“默认 profile 是否绑定 `~/.codex`”做局部修补。
- 真正的最小可行改法是把问题重定义为：
  - 单一运行时
  - 单一账号真相
  - 单一 owner 控制
- 因此推荐路线不是继续增强当前混合态，而是引入“共享模式 / 独立模式”双模式，并把共享模式建立在附着同一 `codex app-server` 之上。
